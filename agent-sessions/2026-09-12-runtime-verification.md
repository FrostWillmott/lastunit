# 2026-09-12 — проверка собранного приложения в рантайме и правки по находкам

Инструмент: Claude Code (CLI). Модель: Claude Opus 5 (Anthropic). Полный
экспорт — `2026-09-12-runtime-verification.jsonl` (см. `README.md` каталога).

Сессия 16:54–18:00 UTC, последняя за 12.09. Задача — не ревью диффа, а прогон
**работающего** приложения: поднять стек и провести все девять пунктов
«Ожидаемое поведение» через реальные интерфейсы. Тесты проекта намеренно не
запускались как доказательство: зелёный `make check` говорит, что проходит
набор, а не что собранное приложение работает.

## Метод

Рабочее дерево было чистым и совпадало с `origin/main`, то есть диффа для
проверки не существовало; область («всё приложение целиком») выбрал владелец.

- Стек поднят на портах **18000/18080**: 8000 и 8080 на машине занимали
  контейнеры других проектов, причём `verbatim-frontend` отвечал 200 на 8080 и
  его легко было принять за фронтенд этого проекта. Развёл оверрейдом compose с
  тегом `!override`; чужие контейнеры не останавливались.
- Браузер (две вкладки одного origin) — витрина, корзина, кабинет, экран
  магазина. `curl` — там, где нужна настоящая одновременность, и как третий,
  не-браузерный клиент SSE.
- Истечение удержания и конец распродажи достигались правкой `expires_at` /
  `ends_at` в БД, а не ожиданием десяти минут; планировщик при этом работал сам.

## Результат

Все девять пунктов и «две вкладки» выполняются. Отчёт с таймингами, таблицей и
тремя скриншотами — **`docs/verification-2026-09-12.md`** (коммит `0fde4b7`).

Три находки, все исправлены в этой же сессии:

| Находка | Коммит |
|---|---|
| Созданная распродажа не доходит до уже открытой витрины (событие не рассылалось) | `f50f060` |
| В фоновой вкладке таймер старта застывает — измерено 27.7 с после границы | `68d0e2b` |
| Отказ карты сохраняет удержание, и это нигде не описано | `3c3de7c` |

Пункт 1 в README переведён из «partially proven» в **proven** — с явной
оговоркой о том, что *не* утверждается: одновременность с точностью до секунды,
поскольку переключение считает клиентский таймер.

## Что стоит знать о ходе работы

- **Проверял невакуумность обоих новых тестов**: снимал фикс — тест падал,
  возвращал — проходил. Тест, который проходит в обе стороны, ничего не стоит.
- **Одно решение изменил по ходу.** Слушатель видимости сначала был повешен на
  Pinia-стор и **потёк между тестами**: глобальный DOM-listener переживает все
  инстансы стора. Это была бы та же утечка и в приложении, поэтому перенёс во
  вью, где `watch` умирает вместе с компонентом. Появился первый в репозитории
  тест вью.
- **Одно наблюдение отозвал.** «Enter не отправляет форму входа» оказался
  артефактом инструмента: поставил слушатель `keydown` и увидел, что до
  страницы не доходит ни одного события — браузерная автоматизация во второй
  половине сессии перестала доставлять синтетический ввод. В отчёт вынесено
  отдельной оговоркой, вывода о приложении не сделано.
- **Проверка CI по правилу 6** `ci-pipeline.md`: run 34709491863,
  `conclusion=success` на запушенном SHA `3c3de7c`, все четыре объявленных джоба
  (`backend`, `frontend`, `audit`, `docker`) отработали — сверялись имена, а не
  цвет прогона.
- **Уборка.** Тестовые данные удалены из БД (все строки приложения,
  `alembic_version` не тронут), стек снят `docker compose down` **без** `-v`,
  том `lastunit_pgdata` цел, контейнеры чужих проектов не затрагивались.
  Изначальное предположение, что демо-распродажа и магазинный пользователь —
  существующие данные владельца, оказалось неверным: `app/seed.py` создаёт их
  при каждом старте контейнера, поэтому удаление безопасно.

## Секреты в экспорте

Транскрипт проверен перед экспортом: сгенерированных значений
`POSTGRES_PASSWORD` и `PAYSTUB_WEBHOOK_SECRET` в нём **нет** (0 вхождений),
дампов `.env` и значений сессионных cookie нет. Совпадения на
`SEED_SHOP_PASSWORD` — это литерал `shop-password` из `.env.example` и
`tests/integration/test_realtime.py`, то есть значение, уже лежащее в
репозитории.

**Файл отредактирован перед коммитом.** Пароль, который я сам придумал для
тестовых учёток (`buyer1`, `buyer2`, `shopview`), встречался в транскрипте 24
раза, в том числе в виде `password:'…'` внутри JS, выполненного в браузере, —
на этом месте сработал gitleaks. Значение заменено на
`REDACTED-TEST-PASSWORD` во **всех** вхождениях. Настоящим секретом оно не
было: локальная выдуманная строка для учёток в БД, которая к концу сессии
удалена. Исключение в конфиг gitleaks не добавлялось — ослаблять общий гейт
ради одного файла неправильно, правка самого экспорта дешевле и оставляет
проверку строгой.
