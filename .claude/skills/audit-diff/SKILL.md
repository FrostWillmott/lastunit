# Audit a diff

This is the contract for dual review — a second, independent pass over a diff someone
(or some other agent/model) already wrote. Follow the steps in order; don't skip the
gate even if the diff looks small.

## 0. Same-session gate — did this conversation write the diff?

Before anything else, check your own session context: if any part of the diff under
audit was generated, edited, or planned earlier in this same conversation, **stop and
refuse**. Auditing your own output in the same context is a re-read with the same blind
spots, not a second opinion. Ask the user to open a fresh session (clean terminal,
explicit `--model`) and run the audit there.

## 1. Endpoint gate — Anthropic only

Run:

```bash
[ -z "$ANTHROPIC_BASE_URL" ]
```

If `$ANTHROPIC_BASE_URL` is non-empty, **stop and refuse**. Explain why: this session is
running through a non-Anthropic endpoint (see the provider switcher), so the generator
and the auditor may end up being the same underlying model — the audit would be double
payment for one pass, not a second opinion. Ask the user to re-run in an Anthropic-endpoint
session before auditing.

## 2. Threshold — does this diff need dual review at all

If the diff is under ~100 lines **and** touches none of: async code, SQL/migrations,
concurrency, or a security-relevant surface (auth, untrusted input, secrets) — say so,
recommend `make check` as sufficient, and stop. Dual review on a small, low-risk diff is
pure overhead; save it for the diffs where a second pass actually catches something a
single pass would miss.

## 3. Checklist

Walk the diff against each item explicitly — don't silently skip one:

- Blocking I/O inside `async def` code paths (DB/network/file calls not offloaded).
- Lazy loading under `AsyncSession` — relationships must be loaded explicitly
  (`selectinload` etc.), not left to lazy-load.
- Business logic leaking into routers, or HTTP-awareness leaking into services.
- Bare `except:` / `except Exception:`, or raw/implementation-detail exceptions crossing
  a layer boundary.
- Mutable default arguments.
- Tests cover error paths, not just the happy path.
- Migrations reviewed line by line, not just autogenerated and trusted.
- Untrusted input and secrets handled correctly (no injection, no leakage, no
  hardcoded credentials).

## 4. Mechanical check

Run `make check` (or lint + typecheck + tests individually if the project has no
`make check`). Record the result — pass/fail and what ran — in the report. A clean
mechanical check does not replace the checklist above; it's a separate, required signal.

## 5. Output format

- Findings ordered by descending severity.
- Each finding: `file:line`, what's wrong, and the concrete failure scenario (not just
  "this could be a problem" — state what breaks and when).
- End with a verdict: **approve** or **fix-first**, plus exactly what was run to produce
  the mechanical-check signal (step 4).
